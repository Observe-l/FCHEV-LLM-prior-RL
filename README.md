# SUMO-FCHEV HASAC / SAC / TD3 environment

This repository implements a one-second Gymnasium environment for a 7,000 kg fuel-cell hybrid bus driving behind a lead bus through a deterministic SUMO route. The ego policy chooses requested longitudinal acceleration and 50 kW fuel-cell-system output. There is no rule-based following or signal-light supervisor: the policy controls the ego vehicle, subject to the action bounds and drivetrain/battery feasibility. Battery charge acceptance no longer clips an in-range FCS command: surplus DC-bus power is routed to an ideal dump load, while battery current, SOC, and voltage limits remain enforced.

The local source papers are kept under `papers/`. The primary reference is Peng et al. (2024), “Multiple Electric Components Health-Aware Eco-Driving Strategy for Fuel Cell Hybrid Electric Vehicle Based on Soft Actor-Critic Algorithm.” Battery, fuel-cell, and propulsion data are loaded from the existing `dataset/battery/`, `dataset/fcs/`, and `dataset/motor/` files; the original source files are not modified.

## Run

The current `default` Conda environment already contains NumPy, SciPy, PyTorch, Gymnasium, and SUMO 1.19.0 is installed on the machine. From this repository root, the following commands use that environment directly:

```bash
/home/lwh/anaconda3/envs/default/bin/python -m unittest discover -s tests -v
/home/lwh/anaconda3/envs/default/bin/python train.py --algorithm hasac --episodes 1000 --device cuda
/home/lwh/anaconda3/envs/default/bin/python train.py --algorithm sac --episodes 200 --device cuda
/home/lwh/anaconda3/envs/default/bin/python train.py --algorithm td3
/home/lwh/anaconda3/envs/default/bin/python evaluate.py results/<run>/best.pt --episodes 10
```

For a short smoke run, which caps the episode at 64 steps and starts updates after the first eight transitions:

```bash
/home/lwh/anaconda3/envs/default/bin/python train.py --algorithm sac --episodes 1 --max-steps 64 --learning-starts 8 --batch-size 8
/home/lwh/anaconda3/envs/default/bin/python train.py --algorithm hasac --episodes 1 --max-steps 64 --learning-starts 8 --batch-size 8
/home/lwh/anaconda3/envs/default/bin/python train.py --algorithm td3 --episodes 1 --max-steps 64 --learning-starts 8 --batch-size 8
```

Use `--gui` with either script for SUMO-GUI. Training defaults to headless SUMO. `--device cuda` places the policy, critics, and packed replay buffer on the GPU; `--device auto` selects CUDA when available. The MLP path enables TF32 on supported CUDA devices. SUMO and the vehicle/battery simulation remain CPU-driven. Runs record the compute device, replay device, and peak GPU memory in `summary.json`. Use `--seed N` to set the SUMO, NumPy, and PyTorch seeds. Training runs are created under `results/<algorithm>_<timestamp>_seed<seed>/`; an optional `--experiment-name LABEL` adds a readable ablation/comparison label. Each run writes its own SUMO network and route files under `results/<run>/scenario/`, so separate `train.py` processes do not overwrite each other's generated scenes. Directly constructed `FCHEVEnv` instances use separate temporary scenario directories. Run metadata, trajectories, checkpoints, evaluations, and plots are also isolated by run directory. Multiple jobs can therefore run as separate processes; they share machine CPU/GPU resources, so concurrency can reduce throughput. Runs include the resolved configuration, episode summaries, per-step trajectories with all reward terms and component states, policy-unit/raw/bounded/powertrain-limited/executed actions, both vehicles' speeds and accelerations, the live gap and traffic-light state/distance/remaining time, losses, evaluations, the rolling `final.pt`, the best-return `best.pt`, the five highest-return episode checkpoints listed in `top_reward_checkpoints.json`, and `final_episode_<N>.pt` at completion. Episode return is plotted in `episode_reward.png`; dual-policy runs also write separate `driving_agent_episode_reward.png` and `energy_agent_episode_reward.png` curves; `episode_metrics.png` tracks hydrogen consumption, final SOC/SOH and episode length, and `reward_components.png` plots the signed reward contributions across training. The reward plot starts its vertical axis at 0; negative returns are shown at 0 for display but remain unchanged in CSV, and the upper limit follows visible data automatically. `train.py` defaults to 1,000 HASAC episodes, hidden layers `[256, 128, 64]`, gamma 0.9999, a 100,000-transition replay buffer, batch size 64, and fixed HASAC entropy temperature alpha=1. SAC uses automatic entropy tuning; TD3 uses delayed actor updates, twin critics, target smoothing, and clipped exploration noise.

Training reuses the same `--seed N` for every episode reset, so the traffic-light initial phases and lead-vehicle stop plan stay identical throughout a run. The policy's action exploration and training updates still vary. The standalone scenario preview script uses the same seed and environment setup, so its signal-timeline and lead-speed plots represent the scene used for training.

Consecutive stationary time is recorded for diagnostics, but it does not terminate an episode.

HASAC and the independent-SAC baseline use two decentralized policies. The driving actor has 11 observations, in this order: ego acceleration and speed, lead acceleration and speed, following distance, next signal state/distance/phase time remaining, current and next speed limits, and distance to the next speed-control region. Its action is acceleration. The energy actor has five observations: measured executed ego acceleration, battery SOC, battery SOH, FCS SOH, and EDU SOH; its action is requested FCS power. The measured acceleration is the current plant state at the decision boundary (the result of the preceding transition), rather than an unexecuted acceleration request. Independent SAC trains a separate critic and replay for each policy on its own reward partition. HASAC uses one joint replay buffer and twin centralized critics over the concatenated 16-value state and two actions. Both actors optimize the same cooperative reward, `r_team = r_driving + r_energy`, checked against the environment's total reward; per-agent return fields are retained only as diagnostics. The decentralized actors are improved sequentially in a random order, as in the HASAC paper. The environment still applies the same joint physical action and powertrain/battery feasibility constraints. Checkpoints bundle both actors, both critics, and optimizer states.
## Project layout

- `environment/fchev_env.py`: Gymnasium reset/step interface, action constraints, SUMO synchronization, power balance, and reward assembly.
- `environment/sumo_interface.py`, `environment/scenario/`: TraCI integration and reproducible single-lane road generation.
- `util/`: cached source-data loading, vehicle dynamics, battery electrical/thermal/aging model, FCS and EDU models, degradation, observation scaling, and reward functions.
- `algorithm/`: HASAC, independent SAC, TD3, actor/critic networks, and replay buffer.
- `config/default.json`: vehicle, pack, FCS, EDU, reward, SUMO, and training parameters.
- `tests/`: model checks, agent-update checks, and a live SUMO step/power-balance check.
- `results/`: timestamped runs and validation outputs.

## Data interpretation and physical models

The `dataset/battery/README.txt`, `dataset/motor/README.txt`, and `dataset/fcs/README.md` files define the actual file axes, units, matrix orientation, and source limits. These were read before implementation. Lookup tables are loaded once when the environment is created; no files are opened from `step()`.

The battery uses the 2.3 Ah nominal A123 26650 cell model. The 106-series / 134-parallel pack has 349.8 V nominal voltage, 308.2 Ah nominal capacity, 107.81 kWh nominal energy, and 14,204 cells. One representative cell is solved electrically and thermally; pack power, current, and voltage are obtained through the series/parallel scaling. Discharge current is positive. Charge and discharge select their separate source R/C tables. OCV comes from the supplied mean C/20 curve. SOC is limited to 0.15–0.90, current to 2C discharge / 1C charge, and terminal voltage to 2.0–3.6 V per cell. The quadratic pack-power equation is solved with the stable low-current root. The R/C branches use exact first-order discretization; the two-node thermal equations use backward Euler to remain stable at a one-second step. Core/surface capacitance and resistance stay at representative-cell scale. For (R_u), the implementation selects Lin et al. (2014) Table 1 value 3.19 K/W rather than the separate bundled `run_model.m` value of 15 K/W.

Entropy coefficient data are supplied in mV/K and converted to V/K. Lin/Peng Eq. (21) is used for reversible entropy heat, with temperature in Kelvin; ohmic heat remains nonnegative. The measured charge/discharge tables only cover their documented SOC and temperature axes. Queries outside those axes use the nearest boundary value and set `battery_parameter_table_clipped` in step information; the code does not silently extrapolate. A step is rejected if the resulting SOC, current, or terminal voltage cannot satisfy the configured limits.

Battery aging follows Peng et al. (2024), Eqs. (22)–(25), with (z=0.55), (R=8.314), (E_a=31700-370.3c), and the four Table II (B(c)) samples. Eq. (23) gives the one-way amp-hour throughput (Ah_{20}) at 20% capacity loss. In Eq. (25), (C_n) is represented in coulombs, so (N=3600Ah_{20}/C_n) is dimensionless and equals (Ah_{20}/Q_{cell,Ah}). Eq. (22) then uses current in A and elapsed time in seconds, with the factor of two accounting for charge and discharge throughput over a full cycle. `SOH_bat` is the Peng lifetime-health indicator: it decreases to zero at its modeled EOL throughput. The implied physical capacity is mapped from 100% to 80% over that health interval and feeds back into current/SOC limits. (B(c)) is linearly interpolated over the published C-rate samples and clamped below 0.5C (the configured operating current never exceeds 2C); the clamp is exposed as `battery_aging_c_rate_clipped`. Arrhenius temperature is always Kelvin. This is the explicit unit interpretation used by the implementation and tested in `tests/test_models.py`.

The FCS is the original 50 kW Lin and Zheng (2011) polynomial from `dataset/fcs/fcs_parameters.txt`. Hydrogen rate is interpolated directly from the source table and already includes its modeled purge loss. FCS OFF is handled separately with zero hydrogen consumption. A 0.95 DC/DC efficiency is applied between stack output and the DC bus. The first version does not enforce the paper's ramp-rate limit. Song et al. (2020) degradation values are converted from percent to fractions; startup is counted on OFF-to-ON only, low/high power time uses seconds-to-hours conversion, and load-change damage is applied once per power change.

The motor query uses the EPA Generic IPM 150 kW **complete EDU** map, with motor-shaft rpm and torque axes, 9.5 gear ratio, valid operating mask, electric-power map, and total-loss map. It is not a motor-only map: inverter and gearing losses are already included, and component losses cannot be separated. EPA provides no independent regen test data; its regen area mirrors motoring losses with factor 1.05. The implementation builds interpolators once from valid operating-map nodes and rejects queries outside the valid map hull, torque-speed envelope, mechanical power limit, or speed limit. It does not fill invalid cells or extrapolate. EDU electrical power comes from the native electrical-power lookup. EDU loss for CLR comes from the separate valid-region loss lookup and is constrained nonnegative, including regeneration.

EPA does not provide rated power, rated torque, rated efficiency, or a rated operating point. To make Peng's loss-based motor health metric executable, this project uses the user-selected proxy point (75\,kW, 156\,N\cdot m, 4591\,rpm). Its speed/torque product is 74.9999 kW, so the port definitions agree. The point is inside the EPA valid envelope. Interpolation at that point gives approximately 94.32% efficiency from the native electrical-power map, 79.52 kW electrical power, and 4.98 kW loss from the loss map. These are proxy-reference values, not EPA ratings. CLR is accumulated as (P_{loss}dt/(P_{loss,ref}\cdot 30000\,h)); the 30,000 h lifetime is the supplied Peng assumption.

The bus longitudinal dynamics use the configured SI parameters and the current speed/acceleration. Motor speed and torque are derived from wheel force, 0.40 m wheel radius, and the 9.5 ratio. Positive EDU electrical power means motoring; negative means regeneration. The DC-bus balance is (P_{EDU,e}=P_{battery}+0.95P_{FCS}-P_{dump}), with auxiliary loads set to zero. The FCS action is executed at its bounded requested value. Battery power follows the balance equation while inside its dynamic limits; if it would exceed the charging limit, battery charging is clamped at the BMS limit and the excess is recorded as `dc_bus_dump_power_w`. This idealized dump load is an explicit modeling assumption that preserves battery constraints and requested FCS power; its power and the residual balance are logged each step. If requested acceleration exceeds the EDU envelope or battery discharge capability, a bisection search reduces acceleration to a feasible value. During braking, the feasible regenerative torque is used and friction brakes provide the remainder. Step information contains requested and executed acceleration, wheel force/power, motor speed/torque, EDU electrical power/loss, friction-brake force, battery current/power/voltage, FCS power/hydrogen, dump-load power, constraints, and the power-balance residual.

The ego's SUMO speed mode is set to manual. Posted speed limits and the vehicle hard cap are separate: ordinary road segments are posted at 60 km/h, intersection zones at 30 km/h, and vehicle/network `maxSpeed` is 70 km/h. A linear penalty `-beta_speeding*max(0, v-v_limit)` applies whenever speed exceeds the active posted limit; the current experiment pair uses `beta_speeding=100`. Speeding is penalized continuously; red/yellow arrival predictions use `C_non-green=100` in the current experiment pair. Red-light crossings are recorded, and neither event terminates an episode. An acceleration request that would exceed the 70 km/h hard cap is clipped to remaining speed headroom. Collision or overlap still terminates the episode. At zero speed, negative acceleration is clipped to prevent reversing and adds no reward penalty. The plant may reduce acceleration when the EPA EDU map or battery limits make the requested operating point infeasible. The optional 30 km/h intersection zone is enabled by `sumo.intersection_speed_zone_enabled` (default `true`); setting it to `false` removes the reduced-speed area from the ego's speed-limit observation and posted-limit penalty logic and from the lead vehicle's SUMO speed cap, while red-light crossings remain recorded as diagnostic events. When enabled, the zone covers the last 100 m before the stop line and the junction; the lead speed cap begins 200 m before each signal. Normal route completion and time-limit truncation have no terminal penalty. The observation includes the next signal's state (0 red, 1 green, 2 yellow), distance and time remaining to its next phase change, plus current-region speed limit, next-region speed limit and distance to the next speed-control point. Red-signal state, distance, and phase time are represented only by the traffic-light observations; speed-limit observations contain positive posted limits only. Training records the number of signals passed by the ego and lead, speed-limit violations, signal crossings, collision IDs, requested/executed actions, and physical clipping. SUMO's initial one-second call loads the two `depart=0` vehicles; it is an initialization/bootstrap step, not an RL transition. Every subsequent `env.step()` advances exactly one configured one-second SUMO tick. SUMO's position integration is semi-implicit; quasi-steady electrical power uses the mean speed over the transition for the kinetic-energy calculation.

The scenario is one straight, flat, single-lane road with 25 signalized intermediate nodes spaced 1 km apart. At reset, both vehicles start at 0 m/s with a 10 m net gap (ego starts at 20 m; lead starts at ego position + 10 m + 8 m vehicle length + 3 m SUMO minGap); the lead's IDM target speed remains 13 m/s. A gap above 300 m and 1,000 m is recorded for diagnostics only; neither threshold nor lack of progress terminates an episode. Collision/overlap or the lead reaching its terminal stop ends the episode; speeding and red-light crossings are recorded without terminating. The lead reaching its terminal stop is normal completion. The default time limit is 6,000 s. The ego and lead share an unsignalized tail edge, and the lead stops 200 m into that segment. Every adjacent pair of traffic lights has one seeded random lead stop between them, with duration sampled uniformly from 50–100 s. Each signal repeats a fixed 90 s cycle: 40 s green, 3 s yellow, and 47 s red. Every episode seed deterministically assigns a distinct initial position in the signal cycle to each light and a separate random position/dwell duration for every lead stop; repeating the seed reproduces the same scenario. The lead vehicle follows SUMO IDM and slows for intersections; the RL-controlled ego remains manually controlled. The ego observation has 15 elements: the original 9 Peng state variables, next signal state/distance/remaining phase time, current-region speed limit, next-region speed limit and distance to the next speed-control point. Speed limits, distances and times are in SI units; only the categorical signal state is divided by 2. Speed-limit observations are independent of signal phase: outside an enabled 30 km/h zone, the next limit is 30 km/h and distance is measured to that zone entry; inside it, the next limit is 60 km/h and distance is measured through the current junction to the post-signal road; when disabled, both limits remain 60 km/h and distance is 30000 m. Policy outputs are `u=[u_a,u_FCS]` in `[-1,1]^2`; acceleration uses `a=1.5u_a` for `u_a<0` and `a=0.7u_a` otherwise, while FCS power remains `25(u_FCS+1)` kW. The physical actions span `[-1.5,0.7]` m/s² and `[0,50]` kW. Run `python analyze_sumo_environment.py --seed 7` to produce a lead speed-time curve, a signal-by-time state chart, CSV samples, and a JSON scenario specification under `results/environment_preview_seed7/`.

Reward terms are not passed through a soft-normalization function or global multiplier. `D_safe` and `D_max` retain the screenshot equations: `D_safe=2+0.5*v_h+0.0625*v_h^2`, `D_max=10+v_h+0.0825*v_h^2`, with speed in m/s and distances in m. Let `d` be the actual nonnegative following gap in meters, without clipping it to `d_ref`. The following term is `r_follow=beta_0*c_follow`: `c_follow=C_0-C_1*(1-d/D_safe)^3` for `0<=d<D_safe`, `c_follow=C_0` for `D_safe<=d<=D_max`, `c_follow=C_0-C_2*(d-D_max)/(d_ref-D_max)` for `D_max<d<d_ref`, and `c_follow=C_3*Delta_d` for `d>=d_ref`, where `Delta_d=d_(t-1)-d_t` is positive when the gap shrinks. The default settings are `d_ref=200 m`, `beta_0=1`, `C_0=5`, `C_1=10`, `C_2=3`, and `C_3=0.05`; individual experiment profiles can override these values. In the current `z^3` experiment pair, `C_1=500`. For an overlap terminal sample (`d<=0`), the close-gap formula uses `d=0`. If the named lead is not ahead, its 30000 m observation sentinel is marked invalid and excluded from following reward and gap-change calculations. At zero speed, a negative acceleration request is physically clipped to zero by the no-reverse constraint and receives no additional reward penalty; zero acceleration remains valid and unpenalized. The linear speeding penalty `r_speed=-beta_speeding*max(0,v-v_limit)` is applied against the posted current-area speed limit (60 km/h ordinary road, 30 km/h intersection zone), with `beta_speeding=100` in the current experiment pair and speed difference in m/s. Speeding and red-light crossings do not terminate; collision/overlap does. Other terms remain signed penalties: `r_H2=-beta_1*m_H2` (`beta_1=0.2`, hydrogen in g), `r_FCS=-beta_2*(100*ΔCLR_FCS)` (`beta_2=5e3`), `r_battery=-beta_3*(100*ΔSOH_battery)` (`beta_3=1e5`), `r_EDU=-beta_4*(100*ΔCLR_EDU)` (`beta_4=1e5`), `r_comfort=-beta_5*c_comfort` (`beta_5=1`), and `r_SOC=-beta_6*C_SOC` (`beta_6=10`). `c_comfort=abs(a_t-a_{t-1})/2.2`; `C_SOC=abs(SOC-0.5)`. Degradation uses each step's increment in percentage points. The logged following reward can be positive in its target band; the configured coefficients do not mathematically guarantee every step remains within [-5,5]. The driving reward also includes a signal-arrival term: estimate `t1=distance_to_signal/current_speed`; only when `t1 < phase_remaining` is the term active. An observed green phase contributes `beta_7*C_1=+3`, while red or yellow contributes `-beta_7*C_2=-100` in the current experiment pair (`beta_7=1`, `C_1=3`, `C_2=100`). At zero speed or when the phase is predicted to change before arrival, the term is zero. It is included in the driving reward and logged with its prediction time and activation flag. The current default configuration uses HASAC with shared team reward; abnormal termination no longer uses the older -500 value.

The speed-zone anticipation term is enabled per experiment by `reward.reward_coefficients.beta_8`. For a lower upcoming positive speed limit, entry speed is estimated as `v_entry=sqrt(max(0,v^2-2*a_brake*d_entry))`, with `a_brake=0.75 m/s^2`; relative excess is `e=max(0,(v_entry-v_limit)/v_limit)`. The signed reward is `r_zone=beta_8*(e_t-e_(t+1))`, so reducing predicted entry overspeed earns reward and increasing it loses reward. The target is the next lower posted speed limit while approaching a zone, or the current posted cap while inside it. Signal state never changes this target; stopping below the 30 km/h cap at a red light adds no speed-zone reward. The speed-only observation run uses `beta_8=500` and `gamma=0.999`. Its positive speed-zone shaping is suppressed when the active region context changes or on collision termination steps; negative shaping remains active. This prevents the error potential from resetting at an intersection boundary and creating a false reward. Trajectories log predicted entry speeds, errors, distance, target, and reward contribution.

## Verification performed

The training-run summaries below are historical and predate the current 15-state observation, removal of the rule-based following/signal supervisors, red-light termination, and signed following reward; they do not describe the current policy behavior.

The test suite covers data dimensions, battery interpolation/electrical/thermal/aging behavior, EDU/FCS limits, the signed following reward and its units, SAC/TD3 updates, 15-state observations and speed-region encoding, manual action execution, neutral and reverse-directed acceleration requests at rest without action-specific penalties, global-speed-limit termination without clipping, red-light termination, collision/overlap handling, the lead-stop terminal event, and one-step power balance.

Profiling the same 300-step follower-controller simulation before and after the lookup changes showed throughput increasing from 368 to 663 environment steps/s under `cProfile`. Battery-table interpolation calls fell from 10,500 to 4,500 per 300 steps, and their cumulative profiled time fell from 0.341 s to 0.089 s. An unprofiled 1,728-step follower rollout ran at 1,448 steps/s before triggering `gap_limit`. The SAC training throughput includes neural-network updates and was 25.7 transitions/s in the run below; table lookup is no longer the main simulation cost.

The 50-episode SAC run used seed 7 and is saved under `results/sac_20261017_105620_006277_seed7/`. It processed 1,820 transitions in 70.8 s; all episodes ended at `gap_limit`, with 30–49 steps each. Signed returns were -1.237 to -0.804 (mean -0.977); their positive penalty magnitudes were 0.804 to 1.237, inside the requested 0–50 range. There were no collisions or sub-3 m safety violations. This checkpoint did not learn to stay within the 300 m boundary or complete the route, so the short returns reflect early termination rather than good route efficiency. Per-term normalized and scaled statistics are in `reward_statistics.json`; `episodes.csv`, trajectories, evaluations, `best.pt`, and `final.pt` are alongside it.

The 200-episode SAC run used seed 7 and is saved under `results/sac_20261018_113858_954734_seed7/`. It processed 24,716 transitions in 472.0 s. Signed episode returns ranged from -83.577 to -0.747 (mean -3.557); the first and last 20-episode means were -0.966 and -3.369. Terminations were 195 `gap_limit`, 4 `gap_overlap`, and 1 `route_complete`, with no SUMO collisions; 14 episodes contained 511 total sub-3 m safety-violation steps. The best-reward checkpoint is episode 77, which ended after 28 steps at `gap_limit`; it is not evidence of successful route following. The run folder contains the episode-reward curve, 200 episode rows, per-episode trajectories with policy/requested/bounded/executed actions and both vehicle traces, and `best.pt` / `final.pt`.

The best checkpoint was run in SUMO-GUI and remains paused at its final state. The demonstration lasted 35 steps, returned -0.734 (penalty magnitude 0.734), had a 30.46 m minimum gap, and terminated at `gap_limit` with no collision. Its evaluation row is saved as `results/sac_20261017_105620_006277_seed7/evaluation_seed20261018_20261017_105950_603849.csv`.

The CUDA-enabled 200-episode SAC run used seed 7 and is saved under `results/sac_20261018_135553_028967_seed7/`. The policy, critics, and replay buffer ran on the NVIDIA GeForce RTX 4090 Laptop GPU; TF32 was enabled. It processed 101,152 training transitions in 1,189.4 s (85.0 transitions/s) with 76.1 MiB peak PyTorch GPU allocation. Terminations were 174 `gap_limit`, 8 `gap_overlap`, 4 collisions, and 14 lead-stop completions. The best training-return checkpoint was episode 109; a separate evaluation completed the route in 2,419 steps with return -9.199 and no collision. The final policy also completed both periodic evaluations after episode 200. Safety remains inadequate: the 200 training episodes accumulated 20,805 steps with sub-3 m gaps, and the best-checkpoint evaluation's minimum gap was 1.17 m. The run folder contains all 200 trajectories, evaluation rows, checkpoints, summary, and plots.
